# Result Analysis Report

## Purpose

This document explains the intention of the new experiment structure and interprets the current benchmark outputs generated by the report pipeline.

The goal of the upgrade was not just to run more code. The goal was to make the project read like a strong course report by answering three clear questions:

- `RQ1`: Does proactive SLA-aware scaling reduce SLA violations and tail latency compared with baseline policies?
- `RQ2`: What is the cost-performance tradeoff of proactive scaling?
- `RQ3`: Which parts of the SLA-aware design matter most?

The experiments were structured so the report can present:

- one main comparison,
- several robustness checks,
- and one ablation study.

## 1. What the main experiment is trying to show

The main benchmark compares:

- `static`
- `reactive`
- `util_base`
- `sla_aware`
- `sla_aware_ema`
- `forecast_only`

The intention is to show the tradeoff between:

- lower cost,
- lower SLA violation,
- lower p99 latency,
- and better resource efficiency.

## 2. How to interpret the main result

### Clear positive findings

The main comparison does show the intended baseline ordering:

- `reactive` is cheapest, but has the worst SLA behavior.
- `util_base` is a much stronger baseline than `reactive`.
- `static` is more expensive than `util_base`, but still not as good on violation rate.
- all proactive policies drive violation to zero and reduce p99 substantially.

This already supports a useful report claim:

> proactive scaling can greatly improve SLA outcomes, but naive proactive behavior may overpay for that protection.

That is a valid and interesting result. It means the project is no longer just asking whether proactive scaling helps. It is asking whether it helps efficiently.

### Most important limitation in the current result

The proactive policies are too aggressive under the current setup:

- `forecast_only`, `sla_aware`, and `sla_aware_ema` all collapse to almost the same latency outcome,
- all three reach zero violation,
- and the two SLA-aware policies use much more capacity than `forecast_only`.

This means the current report story is:

- proactive methods clearly protect SLA,
- but the current SLA-aware implementations are not cost-efficient enough,
- and the current simulator/workload setting may be too easy once a policy scales aggressively.

This is still report-worthy, but it is not yet a strong claim that SLA-aware is the best policy.

## 3. What each scenario is intended to prove

### Main scenario

The `main` scenario is the headline comparison. It should answer:

- who is cheapest,
- who is safest,
- and what the overall cost-performance frontier looks like.

Current interpretation:

- `util_base` looks like the best practical baseline.
- `reactive` is too slow.
- `static` wastes capacity but still does not eliminate violations.
- the proactive family wins on latency/SLA, but spends heavily.

### Stress scenario: higher QPS

From `report_stress_qps`:

- `static` degrades badly: `viol_rate = 0.36464`, `p99 = 10179.3 ms`
- `reactive` still has noticeable SLA issues
- `util_base` remains relatively strong
- proactive policies still stay at zero violation

Intended interpretation:

- higher offered load exposes the weakness of fixed provisioning,
- and it strengthens the argument that proactive scaling matters under burstier or heavier traffic.

This is a good robustness-check result.

### Stress scenario: stricter SLA threshold

From `report_stress_sla`:

- baseline policies get slightly worse,
- proactive policies remain unchanged.

Intended interpretation:

- the proactive policies are operating so conservatively that even a stricter SLA threshold does not change the outcome.

This is both useful and suspicious:

- useful because it demonstrates strong protection,
- suspicious because it suggests the proactive policies may be overprovisioning so much that the benchmark no longer distinguishes them well.

### Stress scenario: larger boot delay

From `report_stress_boot`:

- `reactive` and `util_base` shift somewhat,
- proactive policies remain almost unchanged.

Intended interpretation:

- proactive methods are supposed to be more robust to boot delay because they act earlier.

This scenario does support that story. However, since the proactive policies are already overscaling, the result is stronger than it should be.

## 4. What the ablation study is intended to prove

The ablation experiment was designed to answer `RQ3`:

- does prediction matter?
- do queue and external signals matter?
- does recent violation history matter?
- does aggressiveness matter?

### Current ablation result

From `report_ablation`:

- `sla_aware_ema`
- `sla_aware_ema_no_prediction`
- `sla_aware_ema_no_queue_external`
- `sla_aware_ema_no_violation`

all produced effectively the same results.

Only aggressiveness changed the output slightly:

- `low_aggr` cost: `809.063`
- base EMA cost: `812.854`
- `high_aggr` cost: `814.125`

### What this means

This is the biggest issue in the current report setup.

The intended message of the ablation was:

> removing an important signal should hurt the policy, revealing which parts of the design are responsible for the gain.

But the actual result says:

> under the current workload and policy thresholds, those removed terms are not materially changing behavior.

That suggests one of these is true:

- the policy is dominated by a few always-active triggers such as current latency or utilization,
- the workload never pushes the policy into a regime where those ablated terms matter,
- or the proactive policy saturates near max-effective scaling so early that the removed terms no longer affect decisions.

This does not invalidate the project, but it does mean the current ablation is not yet strong enough for the final report.

## 5. What the time-window analysis is intended to do

The pipeline automatically chose three time windows:

- `burst`: steps `261-290`
- `stable`: steps `1056-1085`
- `recovery`: steps `309-338`

These windows are meant for qualitative explanation in the report:

- `burst`: show whether proactive policies scale before latency spikes
- `stable`: show whether policies hold too much idle capacity
- `recovery`: show whether policies scale back down safely after demand falls

### What the current windows suggest

From the generated notes:

- `forecast_only` in the burst window keeps about `32.20` instances on average with `0` violation steps
- `reactive` in the burst window averages only `3.80` instances with `2` violation steps

This is exactly the kind of visual explanation the report needs:

- reactive waits too long,
- proactive policies protect latency early,
- but some proactive methods hold far more capacity than the baseline.

So the window analysis is working as intended.

## 6. The real intention behind the whole plan

The intention was not to prove that `sla_aware` already beats everything.

The intention was to restructure the project so the report can make a stronger, more honest argument:

1. `reactive` is too late and gives poor SLA.
2. `util_base` is a strong low-cost baseline.
3. proactive policies can nearly eliminate violations.
4. the hard part is making proactive scaling efficient, not just effective.
5. ablations and stress tests reveal whether the policy logic is genuinely useful or just overprovisioning.

That is a much better report story than:

> here are some benchmark numbers and one policy happened to win.

## 7. What you can say in the report right now

If you wrote the report today using the current outputs, the honest conclusion would be:

> The proactive controllers substantially outperform reactive and static baselines on SLA violation rate and tail latency. However, the current SLA-aware implementations achieve these gains by allocating significantly more capacity, and the EMA-based ablation results suggest that the present workload/setup does not yet clearly separate which predictive signals are responsible for the improvement. Therefore, the main contribution of the project is a reproducible framework for analyzing the cost-SLA tradeoff and exposing where proactive control helps, where it overprovisions, and what must be improved next.

That is a credible course-report conclusion.

## 8. What should be improved next

If you want the report to become stronger, these are the highest-value next steps:

### Priority 1: Make ablations actually separate

Right now the ablations are too flat. Improve this by:

- reducing proactive aggressiveness,
- lowering `max_instances`,
- increasing `qps_scale`,
- increasing `boot_delay_steps`,
- or tightening the SLA threshold further.

The goal is to put the system in a regime where prediction and signal choice actually matter.

### Priority 2: Make one proactive policy the real focus

Use the experiments to choose one:

- either `forecast_only` as the cheaper proactive option,
- or `sla_aware_ema` as the richer but more expensive controller.

Then explain the comparison against `util_base` more carefully.

### Priority 3: Use figures, not only tables

Your report should show:

- one cost vs violation scatter plot,
- one cost vs p99 scatter plot,
- one burst-window figure,
- and one ablation figure.

The figures are what will make the intention of the project clear to readers.

## 9. Bottom line

The experiment plan is working in the sense that it is now revealing the right research questions:

- proactive scaling helps,
- but cost efficiency is the real challenge,
- and your current SLA-aware policies are still too aggressive.

So the new framework is doing what it was supposed to do:

- not just produce numbers,
- but tell you what is strong, what is weak, and what has to be fixed before the final report.
